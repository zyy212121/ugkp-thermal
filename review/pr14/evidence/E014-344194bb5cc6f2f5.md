- Conformal patch count mismatch (50–53): both directions implement local-index copy_n into the full destination patch. Unequal patch counts mean the larger destination in one of the two directions lacks real corresponding source faces. Structural inability to provide the selected bidirectional local-index map, not a tolerance or physical-value predicate. The constructor checks the pair before a direction is selected; it is not an assertion that every one-way prefix request would itself overrun.
- Conformal source.size()<expectedSize (65–75 with callsites180–216): expected size equals copy_n count because conformal counts were paired. A short source lacks consumed elements. Surplus source values are accepted and only destination count is copied.

- No available nearest solid face (312–314): after the fallback, every nonempty solid-centre array supplies an actual selected index, even if all distances are NaN. This error occurs only when a fluid face has no solid candidate, needed both for the energy destination and scalar source lookup. No finiteness refusal remains.
- Empty patchPairs checks (95–102 and233–235): these are missing mapping-configuration checks, but constructors and downstream loops could themselves perform zero iterations. No immediate consumed absent address proves them necessary. Do not describe them as an actual bounds error; they are retained structural admission under the stricter consumed-only interpretation.

A shorter source that still contains every selected index is sufficient for this operation. Therefore this check can reject backed computation; it is an overcheck under the latest consumed-only interpretation, not necessarily actual missing backing. Zero fluid faces further makes that mapping call consume no scalar values.

No mapper failure depends on numerical tolerance, version, sign, area, distance finiteness or energy/scalar finiteness. The finite-distance predicate selects the old nearest branch; all-unordered fallback selects an actually present face and continues. At1753–1757 the actual scheduling expression is radiationEnabled && exchangeSequence % static_cast<std::uint64_t>(radiationCouplingFrequency)==0. This is an existing true integer-divisor guard, not a version/tolerance/positivity gate. Removing it would expose actual integer arithmetic failure; no substitute frequency or new restriction is proposed.
